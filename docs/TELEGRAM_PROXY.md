# Telegram прокси

Встроенный MTProto-прокси работает в процессе Zapret.Desktop.exe. Отдельные EXE, Python и установка зависимостей не нужны. Автор оригинального TG WS Proxy — [Flowseal](https://github.com/Flowseal/tg-ws-proxy); реализация адаптирована на C# по ревизии [2085861957070eeea07990a522b29f42e5230210](https://github.com/Flowseal/tg-ws-proxy/tree/2085861957070eeea07990a522b29f42e5230210).

## Подключение

1. Откройте «Telegram прокси» после «Списки» и нажмите «Запустить прокси».
2. При первом запуске создаётся случайный 128-битный ключ и локальная конфигурация. По умолчанию используется только 127.0.0.1:1443.
3. Нажмите «Открыть в Telegram» и подтвердите добавление прокси в Telegram Desktop. Ключ и адрес показаны в карточке подключения.
4. Ручная настройка: Telegram → Настройки → Продвинутые настройки → Тип подключения → Прокси → MTProto. Сервер: 127.0.0.1, порт и ключ берите из карточки подключения работающего сервера. Ключ включает префикс dd.

Если порт занят, откройте «Настройки прокси», измените порт, сохраните и повторите запуск. Изменения порта, ключ и маршрутов требуют остановки и повторного запуска прокси. До перезапуска карточка подключения показывает фактически работающую конфигурацию.

Сервер, подключённый TCP-клиент и передача данных — разные состояния. Счётчики подтверждают передачу байтов, но не доставку сообщения, воспроизведение медиа или звонок в Telegram.

## Настройки и данные

Автозапуск по умолчанию выключен. Опция «Автоматически запускать вместе с Zapret Desktop» запускает прокси только при открытии Desktop. Для запуска самого Desktop при входе в Windows используйте его существующую настройку автозапуска. Служба zapret не запускает встроенный Telegram прокси.

Ключ всегда виден в карточке подключения. Кнопка с круговой стрелкой справа создаёт новый ключ; работающий прокси автоматически перезапускается на том же порту. После смены нажмите «Открыть в Telegram» и подключитесь заново. Кнопки копирования и отдельное подтверждение смены ключа отсутствуют.

Конфигурация — %LOCALAPPDATA%/ZapretDesktop/telegram-proxy.json. Ключ защищён Windows DPAPI CurrentUser и не переносится на другую учётную запись. Этот файл намеренно не включается в экспорт ZIP, отчёты и журнал. Обычные параметры видимы в JSON. Повреждённый файл не перезаписывается автоматически: закройте Desktop, сохраните его отдельную копию и переименуйте telegram-proxy.json для создания новой конфигурации при следующем запуске. Понадобится повторное подключение Telegram.

Ошибка отображается на странице. События работы также доступны в разделе «Логи». Подробное журналирование добавляет только счётчики и названия маршрутов; ключ, ссылки подключения и содержимое Telegram-трафика не записываются.

## Маршруты

По исходникам Flowseal: основные WS-адреса перенаправляют DC2 и DC4 на 149.154.167.220. Для остальных DC используются резервные маршруты. В поле «Датацентры Telegram (DC → IP)» можно изменить или очистить таблицу. Указывайте по одному правилу на строку, например:

```text
2:149.154.167.220
4:149.154.167.220
```

Допустимы production DC 1–5 и 203; test DC 1–3 распознаются из init с добавлением 10000. Знак DC обозначает media. Production/test IP и домены Telegram взяты из фиксированной ревизии upstream.

Порядок: WebSocket к Telegram (TLS, /apiws или /apiws_test), собственный Worker (/apiws?dst=IP&dc=ID), CfProxy (для media сначала HTTP/2 /api), прямое TCP к исходному Telegram DC:443. Ошибка установления соединения позволяет перейти к следующему маршруту. После передачи init/пакетов прозрачного переключения маршрута нет: соединение закрывается, Telegram переподключается. TCP можно явно запретить. Worker требует уже настроенного пользователем сервера, развёртывание Worker приложением не выполняется. CfProxy использует встроенный список доменов из указанной ревизии либо явно заданный список. Автоматического обновления списка с GitHub нет.

Каждое семейство маршрутов имеет ограниченное время подключения, ошибки вызывают backoff 30–3600 секунд. TLS проверяет цепочку и имя сервера, редиректы не выполняются. Режим domain fronting upstream, отключающий hostname verification, исключён. Отключения TLS и открытого внешнего listener нет.

Ограничения: 64 локальных клиента по умолчанию (не больше 256), 8 одновременных установлений upstream, init timeout 10 секунд, idle timeout 300 секунд, ограниченные размеры MTProto/WS/HTTP2-пакетов. HTTP/2 использует штатный стек .NET, два одновременных POST на соединение, ограниченную очередь ответов и повтор последнего небольшого зашифрованного запроса до трёх попыток в окне 30 секунд. В отличие от upstream нет пула предварительно открытых WS и общей H2-lane между локальными клиентами; полная эвристика истории/replay и lane rotation Python-версии не перенесена. Это различие может влиять на сложные media-сценарии; оно требует отдельной проверки на реальном аккаунте.

Локальные серверные режимы upstream Fake TLS/masking и HAProxy PROXY header не включены: приложение принимает только локальный obfuscated MTProto, ссылка dd. Модуль обновляется только вместе с Desktop.

## Жизненный цикл

Остановка, смена стратегии, автоподбор и обновление дистрибутива zapret не управляют прокси. Остановка прокси не управляет winws, WinDivert и службой. Сворачивание/скрытие окна оставляет процесс и прокси работающими. В существующем трее есть статус, запуск/остановка, переход к странице и открытие Telegram. Полный выход останавливает подключения и освобождает порт; после завершения процесса Windows также закрывает его сокеты. Внешнего процесса для продолжения работы не создаётся. Обновление Desktop завершает встроенный сервер вместе с Desktop; при следующем запуске применяется сохранённый явный выбор автозапуска.

## Проверки

Автотесты: NIST AES-256-CTR, MTProto init, signed/test DC, фрагментация, пакетные границы, плохой ключ, лимиты, start/stop/restart, занятый порт, loopback TCP с перешифрованием, локальный TLS/WebSocket/HTTP2, отклонение неизвестного сертификата, таймауты, порядок fallback/backoff, DPAPI, повреждённый JSON, UI/трей и независимость от Zapret. Скриншоты headless UI проверяются в светлой/тёмной теме на 1440×900 и 1200×800.

Реальные анонимные запросы req_pq_multi через встроенный сервер получили корректный resPQ с совпадающим nonce от Telegram через каждый из четырёх маршрутов: основной WebSocket, CfProxy WebSocket, CfProxy HTTP/2 (media DC4) и прямой TCP. Это подтверждает сетевой путь и криптографию, но не заменяет проверку Telegram Desktop с аккаунтом. Вручную остаётся проверить текстовые сообщения, фото/видео, загрузку крупных файлов, звонки, CfProxy/Worker в сети пользователя, native tray, второй экземпляр Desktop и завершение Windows.

## Сообщения о соединениях

Сбой отдельного соединения не означает остановку локального сервера. Такие события записываются как WARN с датацентром, маршрутом, этапом и безопасным кодом причины, например WebSocket: ConnectionClosedPrematurely. В статистике сохраняются число сбоев, отклонённых клиентов и время последней проблемы. Ошибки запуска/работы самого listener по-прежнему отображаются в основной карточке.

Закрытие клиента и отмена второй стороны при завершении сеанса не создают новую сетевую ошибку. Первоначальная причина реального сбоя сохраняется. Предупреждение о ключе/транспорте означает, что локальный клиент не прошёл проверку MTProto; после смены ключа заново подключите Telegram через кнопку «Открыть в Telegram». По старому общему сообщению «Некорректный MTProto init или пакет» определить точный этап было невозможно; теперь этапы разделены.

## Карточка и сообщения

На главной карточка находится рядом с доступностью сервисов; ниже 1100 px обе карточки занимают всю ширину и располагаются друг под другом. В двух колонках их высота совпадает. Кнопка «Остановить прокси» повторяет красное оформление остановки Zapret. При запуске и остановке кнопка показывает индикатор, повторное нажатие заблокировано. Результаты запуска, остановки, сохранения параметров и обновления ключа выводятся в нижней строке сообщений. Минимальная высота окна с разделом прокси — 740 px: навигация и авторы остаются видны.

Первое предупреждение о соединении записывается сразу. Одинаковые предупреждения за 30 секунд объединяются в строку с количеством дополнительных повторений; разные датацентры, этапы и причины остаются отдельными. При остановке оставшиеся повторы записываются сразу. Счётчики ошибок и отклонённых клиентов учитывают каждое событие.
